Create a new system package that satisfies the convention.

Input: the kind (rag, agent, api, worker) and optionally a stack preference.

If no stack is given, use the project's default from .env
(FRAMESTACK_DEFAULT_STACK_<KIND>), and if that is absent, ask once and record the
answer there.

Known stack preferences, all equally valid:
  agent  — langgraph | pydantic-ai | plain
  rag    — pgvector | qdrant | chroma
  api    — fastapi | litestar
  worker — postgres-queue | arq

The stack affects only what you write inside the package. It never affects the
package name or its exports.

Produce:
  <kind>/__init__.py        re-exports the required symbols
  <kind>/settings.py        one BaseSettings subclass, only behavioural values
  <kind>/<implementation>   the layout below, for api and agent
  tests/test_<kind>.py      at least one test per required export

The test must call the export and assert something real. A test that only imports
the module is not acceptable.

If the package already exists, stop and say so. Do not overwrite.

### The layout, for api

  api/__init__.py       exports app
  api/settings.py
  api/routes/           one module per resource, never one module for all of them
  api/deps.py           auth, database session, repository construction
  api/schemas.py        request and response models

Rules, and they are not stylistic:

  A route handler is at most five lines: call a service, return a response. A
  handler with logic in it cannot be read back — the interface traces a request by
  the names a handler calls, and forty lines of branching has no single answer to
  "where does this go next".

  Business logic lives in services/ at the project root, never in api/. The api is
  transport.

  Request and response models live in schemas.py, never inline in a handler.

  Everything a handler depends on is built in deps.py and injected. A handler that
  constructs its own database session is a handler nobody can test.

### The layout, for agent

  agent/__init__.py     exports run
  agent/settings.py
  agent/supervisor.py   or loop.py, or graph.py — whichever the stack calls it
  agent/prompts.py      the prompt text, out of the code that sends it
  agent/tools/          one file per tool

  One tool per file, and no god-module. Each of those files is a node in the
  interface, so a file with six tools in it is one box where there should be six —
  and a person cannot see what the agent can do.

### The layout, for rag

  rag/__init__.py       exports search and index
  rag/settings.py       chunk size, top_k, the embedding model -- behavioural values
  rag/store.py          where a document goes and how it comes back
  rag/chunking.py, rag/embeddings.py, and whatever else the implementation needs

Write the store. A `rag/` whose index is a promise -- a TODO, an in-memory dict
standing in for a database, a client constructed and never called -- is a package
that satisfies the convention and does nothing, and `index` is half of what this
kind is for.

Where the store lives depends on the stack, and this is the part that decides
whether the canvas shows a line.

For pgvector, the storage is the project's own and goes in the place this project
already keeps storage:

  repositories/models.py     a declarative model with __tablename__ and a vector
                               column -- the chunk, its embedding, its source
  repositories/settings.py   one BaseSettings field whose default is the
                               postgresql:// URL for local development
  repositories/__init__.py   the engine, the session and the queries; the only
                               place in the project that holds a session
  rag/ imports from repositories/ and never builds an engine of its own

That is not a style rule. The interface reads `__tablename__` and the connection
string out of the project's own Python, and it draws the edge from the import --
so a rag that writes its own `create_engine` beside a `repositories/` that also
has one is a project stating two databases, and a rag with no storage code at all
is a rag with no line to one. Neither is a bug in the drawing; both are the
picture being right about code that is wrong.

If the project already has `repositories/`, add to it. Never a second ORM beside
one that is there, and never a migration you were not asked for.

For qdrant or chroma there is no `repositories/` and no model: the client goes in
`rag/`, its URL or path goes in `rag/settings.py`, and nothing is written that
implies a Postgres the project does not have.

If `compose.yaml` exists and the stack is pgvector, add a service for it, pinned
to a specific `pgvector/pgvector` tag, so the URL in settings points at something
that can actually be brought up. If there is no compose.yaml, do not create one --
that is a different command, and a file invented here is one nobody asked for.

Both tests must pass with the database down, using a fake or an injected session.
A suite that needs a container running is a suite that fails the moment nobody
started one, and nothing here starts anything on its own.

A worker takes however many modules its implementation needs. There is no layout
imposed on it, because nothing in the interface reads its insides.

### Creating a nested system

When the user asks for a sub-agent, or for a system inside an existing one, create
it under the plural directory:

  agent/agents/<name>/__init__.py     exports run
  agent/agents/<name>/settings.py     optional
  tests/test_agent_<name>.py          at least one test

The parent must already exist. If it does not, create the parent first and say so.

The parent is responsible for calling its children. After creating a child, wire
it into the parent's supervisor — an unreferenced child is a package nobody uses,
not a sub-agent. If you cannot see how it should be wired, ask.

Do not nest a second level. If the user asks for a sub-agent of a sub-agent,
explain that the convention stops at one level and propose a flat sibling instead.
